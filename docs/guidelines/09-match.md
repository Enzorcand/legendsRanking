# Etapa 12 — Match

## Objetivo

Depois que o elo Solo/Duo é sincronizado (etapa 11), buscar e persistir as partidas Ranked Solo/Duo de uma `RiotAccount`, de forma idempotente (não duplicar partida já salva). É a base de dados sobre a qual `PlayerStats` (etapa 13) vai calcular win rate, lane principal e campeão mais jogado — nenhum desses cálculos acontece aqui.

## Escopo

Implementar apenas:

- entidade `Match`, guardando só o que é relevante para as estatísticas futuras (sem dados de "replay" completos);
- migration `V6` criando a tabela `matches`, com `riot_match_id` único (idempotência);
- `MatchRepository`;
- `MatchSyncService`, que busca os IDs de partida mais recentes via `RiotApiClient.getMatchIdsByPuuid`, filtra por Ranked Solo/Duo, busca o detalhe de cada partida nova via `getMatchById` e persiste;
- acionar essa sincronização logo depois do sync de ranked, dentro do mesmo fluxo de `RiotAccountService.linkAccount` — sem quebrar o vínculo se a Riot API falhar;
- testes unitários do novo serviço e do hook em `RiotAccountService`.

Não implementar nesta etapa:

- `PlayerStats`, win rate, lane principal ou campeão mais jogado (etapa 13) — dependem das partidas persistidas aqui, mas o cálculo em si é de outra etapa;
- `GET /api/players/{id}/matches` ou qualquer endpoint HTTP (etapa 16) — `Match` ainda não é exposta por nenhuma rota;
- `POST /api/me/riot-account/sync`, cooldown, scheduler (etapas 17/18) — o sync desta etapa acontece só uma vez, no momento do vínculo, igual ao de ranked na etapa 11;
- backfill profundo do histórico: cada chamada de sync busca só a página mais recente da Riot API (até 100 partidas) e para assim que encontra uma partida já salva. Isso cobre bem o caso comum (poucas partidas desde o último sync) mas **não garante importar a temporada inteira de um jogador com centenas de partidas em uma única chamada** — isso é uma limitação de MVP aceita deliberadamente, já que paginação profunda e execução em background são naturais das etapas 17/18, quando sync deixa de acontecer só no momento do vínculo.

## Banco de dados

`V1`–`V5` são imutáveis. Nova migration `V6__create_matches.sql`:

```sql
CREATE TABLE matches (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    riot_match_id VARCHAR(30) NOT NULL,
    riot_account_id BIGINT NOT NULL REFERENCES riot_accounts (id),
    season_id BIGINT NOT NULL REFERENCES seasons (id),
    game_start TIMESTAMP NOT NULL,
    game_duration INT NOT NULL,
    queue_type VARCHAR(30) NOT NULL,
    win BOOLEAN NOT NULL,
    champion_id INT NOT NULL,
    role VARCHAR(20),
    kills INT NOT NULL,
    deaths INT NOT NULL,
    assists INT NOT NULL,
    cs INT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uk_matches_riot_match_id UNIQUE (riot_match_id)
);

CREATE INDEX idx_matches_riot_account_id ON matches (riot_account_id);
CREATE INDEX idx_matches_season_id ON matches (season_id);
```

`riot_match_id` único é o que garante a idempotência pedida pelo projeto — mesmo que o mesmo ID seja processado duas vezes (corrida entre sync manual e automático, por exemplo), o banco rejeita a segunda inserção.

## Mapeamento da entidade

| Coluna | Campo Java | Origem |
| --- | --- | --- |
| `riot_match_id` | `String riotMatchId` | `MatchDto.metadata().matchId()` |
| `riot_account_id` | `RiotAccount riotAccount` | conta sendo sincronizada |
| `season_id` | `Season season` | temporada ativa no momento do sync |
| `game_start` | `Instant gameStart` | `MatchDto.info().gameStartTimestamp()` (epoch ms) |
| `game_duration` | `int gameDuration` | `MatchDto.info().gameDuration()` |
| `queue_type` | `String queueType` | fixo `"RANKED_SOLO_5x5"` (só essa fila é salva) |
| `win` / `champion_id` / `role` / `kills` / `deaths` / `assists` | — | do `ParticipantDto` do jogador dentro da partida |
| `cs` | `int cs` | `totalMinionsKilled + neutralMinionsKilled` do participante |
| `created_at` | `LocalDateTime createdAt` | preenchido na persistência |

`role` vem de `ParticipantDto.teamPosition()` — a Riot pode devolver string vazia em casos raros; não validar/normalizar isso aqui (fica para quando `RoleCalculator`, da etapa 13, precisar interpretar lane).

## Regra de sincronização

```text
RiotAccountService.linkAccount sincroniza o ranked (etapa 11)
        ↓
MatchSyncService.syncMatches(riotAccount)
        ↓
RiotApiClient.getMatchIdsByPuuid(puuid, start=0, count=100, queue=420, startTime=início da temporada ativa)
        ↓
Para cada matchId (mais recente → mais antigo):
        ↓
  já existe no banco (riot_match_id)?
        ↓                    ↓
      sim                   não
        ↓                    ↓
   para o loop         busca detalhe (getMatchById)
   (tudo daqui              ↓
   pra trás já       queueId == 420 (Solo/Duo)?
   está salvo)              ↓                  ↓
                           não                sim
                            ↓                   ↓
                       ignora            salva Match com os
                                          dados do participante
                                          que é o dono da conta
```

Assim como no sync de ranked, se `MatchSyncService` lançar uma exceção (Riot API indisponível, rate limit, etc.), `RiotAccountService.linkAccount` deve capturar e seguir em frente — o vínculo da conta nunca deve falhar por causa da sincronização de partidas.

## Testes mínimos

- `MatchSyncService`: salva uma partida nova de Ranked Solo/Duo com os dados corretos do participante (`win`, `championId`, `role`, kda, `cs`);
- `MatchSyncService`: ignora partidas cujo `queueId` não é 420, mesmo que tenham vindo na lista de IDs;
- `MatchSyncService`: para de processar assim que encontra um `riot_match_id` já salvo, sem buscar detalhe dessa partida nem das anteriores a ela;
- `MatchSyncService`: não falha quando a lista de IDs vem vazia (conta sem partidas na temporada ainda);
- `RiotAccountService`: `linkAccount` aciona `MatchSyncService.syncMatches` depois do sync de ranked;
- `RiotAccountService`: `linkAccount` continua retornando sucesso mesmo se `MatchSyncService` lançar uma exceção.

## Critérios de aceite

- nenhuma partida duplicada é salva, mesmo sob sync repetido (constraint no banco + checagem na aplicação);
- somente partidas de Ranked Solo/Duo (`queueId == 420`) são persistidas;
- nenhum cálculo de estatística, lane ou campeão mais jogado foi antecipado;
- nenhum endpoint HTTP novo foi criado;
- falha da Riot API durante o sync de partidas não impede o vínculo da conta;
- a aplicação continua iniciando com `spring.jpa.hibernate.ddl-auto=validate`;
- os testes definidos para esta etapa passam.
