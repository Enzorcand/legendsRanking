# Etapa 07 — Verificação de e-mail

## Objetivo

Depois do cadastro (etapa 06, já implementada), o usuário recebe um código por e-mail e precisa confirmá-lo para que `users.email_verified` passe a `true`. Enquanto não verificado, o usuário continua podendo logar normalmente — a exigência do projeto é que a verificação seja pré-requisito para **participar do ranking**, não para autenticar. A regra que impede um usuário não verificado de entrar no ranking será aplicada nas etapas de cálculo de ranking (13/14), não aqui.

## Escopo

Implementar apenas:

- entidade `EmailVerification`, vinculada a um `User`, guardando um código de confirmação com expiração e uso único;
- geração e envio do código no momento do cadastro (hook a partir do `AuthService.register`, sem duplicar a lógica de criação de usuário);
- `POST /api/auth/verify-email` — confirma o código e marca `emailVerified = true`;
- `POST /api/auth/resend-verification` — invalida códigos pendentes e envia um novo;
- um `MailSender` isolado (interface + implementação com `JavaMailSender`), para que nenhuma outra parte do sistema monte e-mails diretamente;
- migration `V3` criando a tabela `email_verifications`;
- configuração de `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD` via variáveis de ambiente;
- testes unitários do serviço de verificação e dos dois endpoints.

Não implementar nesta etapa:

- `POST /api/auth/forgot-password` e `POST /api/auth/reset-password` — o plano de 22 passos não reserva uma etapa própria para recuperação de senha; tratar como uma etapa separada a ser numerada e planejada depois, reaproveitando a infraestrutura de e-mail criada aqui. Não improvisar esse fluxo dentro da etapa 07;
- qualquer alteração em `POST /api/auth/login` para bloquear usuários não verificados;
- qualquer alteração em `ranking_eligible` ou nas regras de cálculo de ranking;
- rate limiting real de `resend-verification` (isso é etapa 20 — "Segurança/rate limiting"); nesta etapa, apenas invalidar códigos antigos ao reenviar já evita o caso mais óbvio de abuso, mas não é um rate limiter.

## Banco de dados

Migrations `V1` e `V2` são imutáveis. Criar `V3__create_email_verifications.sql`:

```sql
CREATE TABLE email_verifications (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users (id),
    code_hash VARCHAR(255) NOT NULL,
    expires_at TIMESTAMP NOT NULL,
    consumed_at TIMESTAMP,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_email_verifications_user_id ON email_verifications (user_id);
```

Guardar o código com hash (reaproveitar o `PasswordEncoder`/`BCryptPasswordEncoder` já configurado em `SecurityConfig`), nunca em texto puro — mesmo sendo um código de 6 dígitos de curta duração, é dado sensível o suficiente para não logar nem persistir em claro.

## Regras do código

- código numérico de 6 dígitos, gerado com `SecureRandom`;
- expira em 15 minutos (`expires_at`);
- uso único: ao ser consumido com sucesso, marcar `consumed_at`;
- ao reenviar (`resend-verification`), invalidar (marcar como consumidos, sem sucesso) todos os códigos pendentes anteriores do usuário antes de gerar um novo — evita que um código antigo vazado continue válido depois de um reenvio;
- usuário já verificado que chama `resend-verification` não deve gerar um novo código nem reenviar e-mail (resposta idêntica à de sucesso, para não vazar se o e-mail existe/já está verificado).

## Contrato HTTP

```http
POST /api/auth/verify-email
Content-Type: application/json

{
  "email": "aluno@pucrs.br",
  "code": "123456"
}
```

Resposta `200 OK` quando o código é válido e ainda não expirou; `400 Bad Request` para código inválido, expirado ou já usado.

```http
POST /api/auth/resend-verification
Content-Type: application/json

{
  "email": "aluno@pucrs.br"
}
```

Resposta `202 Accepted` sempre que o payload for válido, independentemente de o e-mail existir ou já estar verificado (evita enumeração de contas). O envio real só acontece quando o usuário existe e ainda não está verificado.

Ambos são públicos (sem autenticação) — adicionar em `SecurityConfig`:

```text
POST /api/auth/verify-email          → público
POST /api/auth/resend-verification   → público
```

## Testes mínimos

- `EmailVerificationService`: gera código, envia e-mail e persiste com expiração correta;
- `EmailVerificationService`: confirma com sucesso um código válido e marca o usuário como verificado;
- `EmailVerificationService`: rejeita código inexistente, expirado ou já consumido;
- `EmailVerificationService`: reenvio invalida códigos pendentes anteriores antes de criar um novo;
- `EmailVerificationService`: reenvio para usuário já verificado não dispara novo e-mail;
- controller: `400` para código inválido, `200` para código válido, `202` para reenvio;
- usar um `MailSender` mockado nos testes — nenhum teste deve depender de um servidor SMTP real.

## Critérios de aceite

- todo usuário recém-cadastrado recebe um código de verificação;
- `emailVerified` só se torna `true` através do endpoint de confirmação;
- nenhuma senha, token ou código aparece em log;
- `login` continua funcionando independentemente do estado de verificação;
- nenhuma lógica de ranking foi antecipada;
- os testes definidos para esta etapa passam.
