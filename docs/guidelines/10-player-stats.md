# Etapa 13 — PlayerStats

## Objetivo

Depois que as partidas Ranked Solo/Duo da temporada estão persistidas (etapa 12), calcular e persistir as estatísticas agregadas de um jogador — total de partidas, vitórias, derrotas, win rate, lane principal e campeão mais jogado — evitando recalcular isso a cada request do ranking/perfil.

## Escopo

Implementar apenas:

- três calculadoras puras e testáveis isoladamente: `WinRateCalculator`, `RoleCalculator`, `ChampionCalculator` (prioridade de testes unitários já definida no projeto);
- entidade `PlayerStats`, migration `V7` e `PlayerStatsRepository`;
- `PlayerStatsService.recalculate(riotAccount)`, que lê todas as `Match` da conta na temporada ativa e faz upsert do agregado;
- acionar esse recálculo logo depois do sync de partidas, dentro do mesmo fluxo de `RiotAccountService.linkAccount` — sem depender de chamada à Riot API (é cálculo puro sobre dados já salvos no banco, então roda mesmo que o sync de partidas tenha falhado parcialmente);
- testes unitários das calculadoras e do serviço.

Não implementar nesta etapa:

- `RankCalculator`/ordenação por tier+divisão+LP+winrate+vitórias — isso é da etapa 14 (`Ranking`), que ordena vários jogadores entre si; `PlayerStats` aqui só agrega os dados de **um** jogador;
- qualquer endpoint HTTP — `PlayerStats` ainda não é exposta (isso é `/api/ranking` na etapa 14 e perfil público na etapa 15);
- entidade `Champion`/nome ou ícone de campeão — por ora só guardamos o `championId` numérico; resolver isso para um nome exibível é decisão de apresentação, não de cálculo;
- recálculo periódico via scheduler (etapa 18) — igual às etapas 11/12, o recálculo aqui acontece uma vez, no momento do vínculo da conta.

## Banco de dados

`V1`–`V6` são imutáveis. Nova migration `V7__create_player_stats.sql`:

```sql
CREATE TABLE player_stats (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    riot_account_id BIGINT NOT NULL UNIQUE REFERENCES riot_accounts (id),
    season_id BIGINT NOT NULL REFERENCES seasons (id),
    total_games INT NOT NULL DEFAULT 0,
    wins INT NOT NULL DEFAULT 0,
    losses INT NOT NULL DEFAULT 0,
    win_rate DOUBLE PRECISION NOT NULL DEFAULT 0,
    primary_role VARCHAR(20),
    most_played_champion_id INT,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Diferente de `ranked_stats` (que é referenciada a partir de `riot_accounts.ranked_stats_id`), aqui `riot_account_id` fica na própria `player_stats`, com `UNIQUE`, garantindo o 1:1 — segue o mesmo modelo de `matches.riot_account_id`, mais direto de consultar.

## Mapeamento

| Coluna | Campo Java | Origem |
| --- | --- | --- |
| `riot_account_id` | `RiotAccount riotAccount` | conta sendo recalculada |
| `season_id` | `Season season` | temporada ativa no momento do cálculo |
| `total_games` | `int totalGames` | `matches.size()` |
| `wins` / `losses` | `int wins` / `int losses` | contagem de `Match.win` |
| `win_rate` | `double winRate` | `WinRateCalculator.calculate(wins, losses)` |
| `primary_role` | `String primaryRole` | `RoleCalculator.mostPlayed(...)`, `null` se não houver partidas |
| `most_played_champion_id` | `Integer mostPlayedChampionId` | `ChampionCalculator.mostPlayed(...)`, `null` se não houver partidas |
| `updated_at` | `LocalDateTime updatedAt` | atualizado a cada recálculo |

Empate na lane/campeão mais jogado é resolvido de forma determinística: maior contagem vence; em caso de empate, desempata pela própria lane/`championId` em ordem crescente — para as calculadoras serem puras e o resultado não depender da ordem de iteração do banco.

## Estrutura sugerida

```text
portfolio.pucrs.match
├── calculator
│   ├── ChampionCalculator
│   ├── RoleCalculator
│   └── WinRateCalculator
├── entity
│   └── Match                    (não mexer)
└── repository
    └── MatchRepository          (adicionar findAllByRiotAccountIdAndSeasonId)

portfolio.pucrs.riot
├── entity
│   └── PlayerStats               (novo, ao lado de RankedStats)
├── repository
│   └── PlayerStatsRepository
└── service
    ├── PlayerStatsService        (novo)
    └── RiotAccountService        (chama PlayerStatsService depois do MatchSyncService)
```

`PlayerStats` fica no pacote `riot` pelo mesmo motivo que `RankedStats`: é um atributo computado de uma `RiotAccount`, não um domínio próprio. As calculadoras ficam em `match.calculator` porque operam sobre `Match`, não sobre `RiotAccount`.

## Testes mínimos

- `WinRateCalculator`: `0` vitórias e `0` derrotas retorna `0.0` (sem divisão por zero); casos normais de proporção;
- `RoleCalculator`: retorna a lane mais frequente; em empate, retorna a alfabeticamente menor; lista vazia retorna vazio;
- `ChampionCalculator`: mesmas regras do `RoleCalculator`, mas por `championId` (empate resolvido pelo menor id);
- `PlayerStatsService`: agrega corretamente `totalGames`/`wins`/`losses`/`winRate`/`primaryRole`/`mostPlayedChampionId` a partir das partidas da temporada ativa;
- `PlayerStatsService`: conta sem nenhuma partida ainda recebe um `PlayerStats` zerado (`totalGames = 0`, `primaryRole = null`, `mostPlayedChampionId = null`), não fica sem registro;
- `PlayerStatsService`: um segundo recálculo atualiza a linha existente em vez de criar outra;
- `RiotAccountService`: `linkAccount` aciona `PlayerStatsService.recalculate` depois do sync de partidas, e continua retornando sucesso mesmo se o recálculo lançar uma exceção.

## Critérios de aceite

- toda `RiotAccount` vinculada recebe um `PlayerStats` (mesmo que zerado, se ainda não há partidas);
- o cálculo considera só as partidas da temporada ativa;
- nenhuma ordenação entre jogadores nem endpoint novo foi antecipado;
- a aplicação continua iniciando com `spring.jpa.hibernate.ddl-auto=validate`;
- os testes definidos para esta etapa passam.
